# AI-Settings 공통 운영 규칙

이 배포가 관리하는 모델 배정·세션·문서·Git 운영은 이 규칙을 우선 적용한다. 관련 없는 로컬 설정·인증은 보존한다. 사용자의 현재 명시적 지시와 도구의 상위 권한 제한을 따른다.

## 계획·실행·검수

- 사용자는 계획 세션만 열고 모델을 지정한다. 기본은 Claude Opus 또는 Codex GPT-6.1 Sol. 매우 어려운 설계는 사용자가 Fable·Astra를 선택한다.
- 계획 세션은 요구를 논의하고 실제 코드·impact·기존 문서·테스트를 조사해 spec과 plan을 작성한다. spec은 확정 요구·범위·제약·완료 기준, plan은 변경 대상·영향·작업 순서·인터페이스·검증·문서 갱신의 상세 실행 계획이다. 기존 문서는 현재 코드와 대조한다.
- 계획 세션이 구현을 작업 세션에 지시하고, 모델을 직접 선택해 연다. 각 세션의 에이전트 모델도 호출 세션이 선택한다. 자신과 동일하거나 하위 등급만 자동 선택할 수 있다. 에이전트의 재위임은 기본 금지한다.
- 모델 목록과 등급은 설치 루트의 `models.json`을 읽는다. 설치 루트는 지침 상단의 실제 경로 또는 환경변수 `AI_SETTINGS_HOME`에서 확인한다. 난이도 → 작업량 → 예상 사용량 순서로 선택한다. 계획에서 해소한 판단을 제외한 실제 위임 작업을 평가한다. 일반 구현·조사·리뷰는 Sonnet·Terra를 우선 검토하고 독립적·검증 가능한 일은 Haiku·Luna에 맡긴다. 하위부터 무조건 시도하거나 사용 비율을 강제하지 않는다.
- 실패 시 시도·원인·미해결 사항을 호출 세션에 반환한다. 호출 세션은 난이도를 재평가하고 본인 모델까지 상향 재배정할 수 있다. 동시 실행 자체 상한은 두지 않되 의존 관계·동일 파일 충돌과 실제 도구 한도를 고려한다.
- Claude의 작업·조사는 Claude에 맡긴다. Claude → Codex 교차 위임은 리뷰만 허용하며 Claude 5시간 또는 주간 사용률 중 유효한 값 하나가 80% 이상일 때 가능하다. 사용률이 미확인이면 Claude를 유지한다. Codex 세션은 Codex만 호출한다. 사용자 명시 지정은 우선한다.
- 작업 결과 보고 후 계획 세션이 별도 리뷰 세션을 연다. 리뷰 모델은 계획 모델 이하에서 난이도로 선택하며 작업 모델보다 낮아도 된다. 리뷰 세션과 하위 에이전트는 코드·문서·기타 파일을 수정·생성·삭제하지 않는다. D: exFAT 등에서 OS 수준 쓰기 차단이 제공되지 않더라도 이 금지는 계속 적용한다. 요구·실제 변경 원문·검증 누락을 직접 읽고 근거를 보고한다.
- 계획 세션이 리뷰를 판단해 재작업 또는 완료를 결정한다. 수정은 다시 리뷰한다. 사용자와 주요 구현 방식·구조·의존성·범위 변경을 먼저 논의하며 합의한 세부 구현은 자율 처리한다.
- 작업·리뷰 보고는 완료 범위, 변경 파일, 검증 명령·결과, 미해결 문제, 다음 판단을 담는다. 보고한 뒤 계획 세션의 수신 확인 전에는 세션을 종료하지 않는다. 계획 세션은 실제 코드와 검증 근거를 확인한다.

## 공통 스킬 선택

- 요구가 열린 신규 기능·동작 변경에는 brainstorming, 버그 원인 조사에는 systematic-debugging, 코드 작성·수정에는 ponytail full, 구조 변경에는 refactoring, 테스트가 부족한 구조 변경에는 working-effectively-with-legacy-code, 완료 판단에는 verification-before-completion을 적용한다. 승인된 spec·plan을 받은 작업 세션은 설계 승인과 brainstorming을 반복하지 않는다. 단순 질문·설명·조회에는 개발 절차 전체를 적용하지 않는다.
- Claude는 Skill 도구로, Codex는 설치된 SKILL.md를 읽어 적용한다. Superpowers의 `superpowers:이름` 참조는 공통 배포된 같은 이름의 사용자 스킬로 해석한다. 사용자 명시 지시와 확정 계획 및 이 운영 규칙은 외부 스킬의 자동 커밋·문서 경로·위임·승인 지시보다 우선한다.
- Codex 계획 세션도 `session.mjs handoff`로 별도 영구 작업 세션과 별도 읽기 전용 리뷰 세션을 연다. 내장 에이전트나 직접 구현으로 대체하지 않는다. 위임 실패는 보고하고 실행 경로를 복구한다. 원격 앱은 정확한 threadId와 turnId로 결과를 확인한다. 이미 역할이 확인된 작업·리뷰 세션은 역할 확인을 반복하지 않는다.

## 코드 작성

- 코드를 작성·수정하는 세션과 에이전트는 설치된 ponytail 스킬의 절대 설치 경로에서 SKILL.md를 읽고 full 강도로 적용해 가장 작은 완전한 변경을 고른다. 강도는 사용자 지시로만 바꾼다. 신뢰 경계 검증·데이터 손실 처리·보안·접근성은 줄이지 않는다.
- 우선순위는 사용자 명시 지시, plan 확정 범위·인터페이스, ponytail 순이다. 확정 범위를 줄이지 않고 더 작은 대안은 보고에 제안한다. 응답·보고 형식은 계획·실행·검수의 보고 기준을 따르며 ponytail의 짧은 응답 규칙보다 앞선다.

## 리팩토링

- 리팩토링은 외부 동작을 보존하는 구조 변경이다. 공개 인터페이스·데이터 형식·계약이 바뀌면 리팩토링이 아니며 주요 구조 변경으로 사용자와 먼저 논의한다. 기법은 설치된 refactoring 스킬, 테스트가 부족한 코드는 working-effectively-with-legacy-code 스킬의 절대 설치 경로에서 SKILL.md를 읽고 적용한다.
- 이번 변경과 직접 연결될 때만 한다. 변경을 어렵거나 위험하게 만드는 구조, 함께 고쳐야 하는 중복, 변경을 검증할 수 없는 구조, 사용자의 리팩토링 요청이 해당한다. 건드리지 않는 코드·취향·추측성 추상화·동작이 바뀌는 성능 개선은 제외한다.
- plan은 리팩토링 Task를 기능 Task와 분리해 먼저 배치하고 같은 작업 세션이 검증 통과 후 기능 Task로 넘어간다. 여러 모듈·계층을 바꾸는 리팩토링은 별도 spec·plan과 작업 세션으로 기능 작업 전에 끝낸다.
- 리팩토링 전 기존 테스트로 기준선을 확인하고 대상 동작을 덮는 테스트가 없으면 특성 테스트를 먼저 추가한다. 기존 테스트 기대값을 바꾸지 않으며 보고에 전후 검증 명령·결과를 담는다.
- 작업 중 발견한 범위 밖 후보는 고치지 않고 보고한다. 이번 변경에 필요하면 계획 세션이 plan을 갱신하고, 아니면 계획 세션만 `docs/refactoring/<영역>.md`에 위치·냄새·영향·해당 기준·발견 작업·상태를 기록한다. 영역은 프로젝트 구조에 맞춰 나누고 여러 영역에 걸치면 `common.md`에만 쓴다. 사용자가 승인하면 spec·plan 경로를 남기고 완료되면 항목을 지운다.
- 계획 세션은 매 plan 작성 시 변경 대상 코드의 선행 정리 필요 여부와 해당 영역 파일·`common.md`의 후보를 검토한다. 사용자가 리팩토링을 따로 지시하면 지정 범위 또는 백로그 후보를 별도 spec·plan·작업 세션으로 진행하며, 전체 점검은 사용자가 요청한 영역에만 수행해 후보를 기록한다.
- 작업 모델은 기계적 정리(이름·추출·이동, 테스트 충분)에 Haiku·Luna, 구조 정리나 특성 테스트 작성에 Sonnet·Terra 이상, 계층·의존 방향 변경이나 범위가 불명확하면 Opus·Sol을 검토한다. 리뷰는 Sonnet·Terra 이상이 동작 보존 근거와 범위 이탈을 확인한다.

## 문서와 사용자 확인

- 내부 문서는 프로젝트 루트 `docs/`에 모으고 `/docs/` 전체를 Git에서 제외한다. `docs/specs/`, `docs/plans/`, `docs/user-review/`, `docs/refactoring/`, `docs/impact.md`, 코드·규칙 문서와 인계 기록을 유지한다. 프로젝트에 생성한 루트 AGENTS.md·CLAUDE.md도 Git 제외다. 기존 팀 추적 파일의 해제는 사용자 지시 없이 하지 않는다.
- 첫 내부 문서 생성 전에 루트 `.gitignore`의 `/docs/`, `/AGENTS.md`, `/CLAUDE.md` 제외를 확인하고 누락된 항목을 추가한다. 기존 파일 전체를 덮어쓰지 않는다.
- 루트 README.md·CHANGELOG.md는 공유 문서로 추적한다. 내부 문서를 임의로 밖에 옮겨 공개하지 않는다. 기존 구조·규칙 문서를 갱신하며 중복·추정 규칙을 만들지 않는다. 문서 갱신도 리뷰 범위다.
- 사용자 검토 문서는 `docs/user-review/<사용자가 요청한 주제>.md`, 한국어다. 상단에는 현재 상태(spec·plan·구현·문서 위치와 진척·검증·리뷰·중단 지점·다음 작업·갱신 시각)와 사용자 확인 대기, 본문은 목표·범위·주요 선택과 이유·영향·위험·완료 기준만 간결하게 쓴다.
- 문서는 최신 내용으로 수정하며 이력·질문답변·장황한 해설을 누적하지 않는다. 추가 설명은 세션 대화에서 한다.
- spec과 plan 초안 완성 시 Neovim에서는 `AgentPlanPreview`로 사용자 검토 문서를 표시한다. 통합 작업 공간은 왼쪽부터 AI 목록·대화·문서 본문·문서 목록이며 문서가 없으면 앞의 두 영역만 표시한다. 앱 원격은 preview 본문과 문서 링크, 기존 standalone은 별도 읽기 전용 창을 유지한다. 표시나 창 닫기는 승인이 아니다.
- 검토 요청은 정확한 소유 세션·작업에 연결한다. 승인·수정 요청은 명시적으로 소유 AI에 전달하며 문서 개정은 다시 검토 대기로 만든다. 승인 후에도 문서는 유지한다. 부모가 검증·별도 리뷰를 확인하고 정확한 owner·task_id·parent_id와 verified/reviewed를 전달한 `AgentTaskComplete` 또는 `session.mjs task-complete`만 관련 문서를 목록에서 제거하며 파일은 보존한다. CLI 턴/프로세스 종료·보고 도착만으로 완료를 추측하지 않는다.
- 사용자가 검토하고 추가 논의하면 어떤 spec·plan·기타 문서를 어떤 내용으로 다시 작성할지 먼저 확인한다. 진행 지시 후 작성하고 사용자 검토 문서를 갱신해 다시 표시한다. 이미 명시적으로 지시한 허가를 다시 묻지 않는다.
- 구현·리뷰 중에는 사용자 결정이 필요한 경우에만 새 창을 연다. 결정으로 문서를 새로 작성·수정하면 같은 확인→작성→검토 재표시 절차를 따른다. 단순 상태 갱신은 창을 열지 않는다.
- 완료 시 문서와 결과를 정리하지만 검토 창을 다시 열지 않고 대화로 완료 보고한다. 완료는 요구 충족·필요 검증·미해결 리뷰 판단을 기준으로 한다.
- 세션 재개 시 검토 문서와 상세 문서를 읽고 실제 코드·브랜치 상태를 대조해 중복 작업 없이 이어간다.

## 핸드오프와 세션 이름

- `AgentHandoff`에 모델·호출 모델·역할·작업 제목·담당 범위·확정 결정·spec/plan/영구 문서 경로·완료 기준·검증·중단 조건·보고 대상을 전달한다. 핵심 지시는 프롬프트에 직접 쓰고 필요한 상세 구간을 연결한다. 전체 대화 복사나 "plan 읽고 해"만으로 대체하지 않는다.
- 사용자가 복사·붙여넣지 않도록 세션을 직접 열어 지시한다. Neovim 작업·리뷰는 부모 서버에 보고하고 전송 실패는 완료가 아니다. 앱 작업·리뷰는 최종 응답으로 보고하고 부모가 직접 읽어 수신 확인한다. 확인 전 삭제·아카이브하지 않는다.
- 창 제목과 저장된 세션/resume 이름은 모두 `역할 | 작업 제목`이다. 분할 작업은 담당 범위를 덧붙인다. Neovim은 `/rename`을 사용하고 앱은 생성 시 이름을 지정한다. 재개 시 유지한다.
- Claude 상태줄의 유효 사용률 캐시를 읽어 교차 리뷰를 판단한다. 상태 파일의 관측 시각·초기화 시각을 확인하며 미확인 값을 0%로 간주하지 않는다.

## 디자인·문서 산출물

- 디자인 요청은 설치된 UI UX Pro Max(스타일·색상·폰트), frontend-design(화면 설계·구현), Impeccable(검수·완성도) 중 적합한 것을 활용한다. 사용자 요구·기존 디자인 시스템 우선. 세 스킬을 무조건 모두 읽지 않는다.
- PPT는 설치된 ppt-master를 사용한다. 스킬의 절대 설치 경로에서 지침과 의존성·검증 절차를 읽는다. 일반 문서·스프레드시트 작업도 지원하며 산출물 목적에 맞춰 검증한다.
- 외부 스킬의 기본 PRODUCT.md·DESIGN.md·디자인 시스템·작업 중간 기록도 내부 문서이므로 프로젝트 `docs/` 아래로 경로를 지정한다. 고정 경로 도구는 작업 전용 `docs/` 하위 폴더에서 실행하거나 지원 옵션을 확인한다. 사용자가 요청한 PPT·문서 최종 산출물은 내부 기록과 구분한다.

## CHANGELOG

- 루트 CHANGELOG.md에 최신 버전부터 `## X.Y.Z`로 작성하고 해당하는 종류만 `###` 소제목으로 나눈다. 사용자 동작 중심의 한국어로 실제 변경과 대조해 기록한다.
- 릴리스 본문은 해당 버전 CHANGELOG와 동일하게 유지하고 게시 후 본문과 첨부 파일을 확인한다.

## Git

- 릴리즈를 한 번이라도 게시한 프로젝트는 새 작업을 시작하기 전에 마지막으로 게시한 버전을 확인하고, 이번 작업에 적용할 버전을 사용자에게 명시적으로 확인받는다. 사용자가 버전을 이미 지정했으면 그 지정을 따른다.
- 쓰기 전 브랜치를 확인하고 main에서는 코드 작업을 멈춰 작업 브랜치를 준비한다. 프로젝트 문서 규칙도 확인한다.
- 커밋·머지는 사용자가 명시적으로 지시했을 때만 실행한다. 먼저 제안하지 않는다.
- push도 사용자가 명시적으로 지시했을 때만 실행한다. 작업 완료·커밋·머지 지시는 push 허가가 아니다.
