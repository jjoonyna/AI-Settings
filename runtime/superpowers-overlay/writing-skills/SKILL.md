# Writing skills

Treat skill changes as behavior changes. Identify the triggering situation, existing failure, desired behavior, scope, and verification before editing. Preserve supporting resources and licenses. Keep the name and description discoverable, use concrete triggers, and make the body concise and actionable.

Write representative application and pressure scenarios first, record the baseline, change the guidance, and repeat the scenarios. Test retrieval for reference material, application for techniques, recognition and counterexamples for patterns, and resistance to conflicting incentives for rules. Do not claim an agent behavior test occurred if it was not run. Use automated checks for installation, path and policy consistency where they fit.

The planning session owns spec and plan writing; its internal agents may investigate and analyze designs only. Implementation and skill edits use a persistent work handoff; formal review uses a separate read-only review handoff. Do not delegate implementation or formal review to internal agents. Work sessions do not repeat approved design decisions. Report any test that cannot be run and its limitation.

Ensure examples match the supported tools and current policy. Commit, push, or publish only on explicit user instruction.
