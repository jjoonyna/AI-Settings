# 전역 지침

## 0. 최우선 — `main` 브랜치 쓰기 차단

**파일을 쓰기 직전**에 현재 git 브랜치를 확인한다.

- 현재 브랜치가 **`main` 이면 즉시 "브랜치를 바꿔야 합니다"라고 사용자에게 알리고, 파일 수정·생성·삭제를 일절 진행하지 않는다.**
- 브랜치가 변경된 뒤에만 쓰기를 시작한다.
- 이 규칙은 아래 모든 규칙보다 앞선다.

### 적용 범위 — 쓰기 작업에만 적용된다

| 세션 종류 | 브랜치 규칙 |
|---|---|
| **계획 세션** (Fable + Plan Mode) | **적용되지 않는다.** 파일을 쓰지 않으므로 브랜치와 무관하다. `main` 에서 계획을 세워도 문제없고, **브랜치 경고를 띄우지 않는다** |
| **조사·검수** (`researcher`·`reviewer`) | 동일하게 적용되지 않는다. 읽기 전용이다 |
| **작업 세션** (Opus) 과 구현 (`implementer`) | **적용된다.** 첫 쓰기 전에 확인한다 |

**계획은 브랜치와 무관하며 병렬로 여러 개 돌려도 된다.** 계획 세션은 파일을 건드리지 않으므로 서로 간섭하지 않는다. 여러 주제의 계획을 동시에 세우고 각각 다른 설계 문서에 기록하면 된다. **worktree 로 갈라야 하는 것은 작업뿐**이고, 그 결과를 나중에 머지하거나 순차로 진행할지는 §6 에서 정한다.

## 1. git 및 실행 권한

| 행위 | 규칙 |
|---|---|
| 빌드·테스트·dev 서버 실행 | ✅ 자유롭게 실행한다 |
| git 조회 (`status`·`diff`·`log`·`branch`·`worktree list`) | ✅ 자유 |
| git 변경 (`add`·`checkout`·`stash`·`reset`·`worktree add/remove`) | ⚠️ 실행 **전에** 사용자에게 알리고 승인을 받은 뒤 진행. **예외 하나** — `:AgentMerge` 4단계 검수를 통과한 **임시 worktree**(`<repo>/worktrees/<name>`) 의 제거와 그 브랜치 삭제는 §10 "머지 후 정리" 절차로 승인 없이 수행한다 |
| **커밋** | 🚫 **먼저 꺼내는 것 자체가 금지.** 사용자가 타이핑으로 지시하고 **커밋 메시지 내용과 이슈번호를 지정**한 경우에만 수행한다 |
| **머지** | 🚫 **동일.** 사용자가 타이핑으로 "머지하라"고 말한 경우에만 수행한다 |
| **push** | ❌ **절대 금지.** 오직 사용자만 한다 |

**`-a` 계열 브랜치·태그**(`hotfix/v*-a`, `v*-a` 등 다른 납품업체용 커스터마이즈 계보)는 본선에 머지하거나 그 반대로 하지 않는다 — 이 규칙은 `:AgentMerge` 뿐 아니라 모든 git 변경 작업에 적용된다(세부는 §10 하드 가드).

**커밋·머지에 대한 금지의 범위를 오해하지 말 것.** 실행만 금지가 아니라 **화제로 꺼내는 것부터 금지**다. 다음은 모두 위반이다:

- "이제 커밋하시면 됩니다"
- "커밋할까요?"
- "머지를 진행할까요?"
- 커밋 메시지를 먼저 제안하는 것

작업이 끝나면 **변경된 파일만 보고하고 그 다음 단계에 대해서는 침묵한다.** 사용자가 먼저 말한다.

## 2. 역할별 세션 구조

**전제: 서브에이전트는 사용자와 대화하지 못한다.** 한 번 dispatch 되면 격리된 컨텍스트에서 실행되고 결과만 반환한다. 그런데 계획은 사용자와 길게 주고받는 작업이다. 따라서 **역할 분담의 주력은 "부모 모델이 다른 세션"** 이고, 서브에이전트는 그 세션 안에서 노동을 대신하는 도구다.

| 세션 | 부모 | 부모가 하는 일 | 하위에 맡기는 일 |
|---|---|---|---|
| **계획 세션** | Claude Fable 5.1 (effort `low`) + **Plan Mode** | 판단·결정·사용자와 대화·설계 문서 작성 | `researcher` 가 **꼼꼼히 조사**해 결론만 요약 반환 |
| **작업 세션** | Claude Opus 5 | 계획 준수 감독·조율·작은 판단·**리뷰 직접 수행** | `implementer` 코드 작업, `researcher` 추가 조사 |

**왜 조사를 하위에 맡기는가.** 꼼꼼히 찾아보게 하면 파일 원문이 쌓인다. **부모가 직접 읽으면 그 원문 전체가 부모 컨텍스트에 남아 매 턴 입력 토큰으로 재청구된다.** 하위가 읽고 **요약만 돌려주면** 부모는 결론만 갖는다. 조사량이 많을수록 격차가 커지고, 부모가 Fable 일 때 차이가 가장 크다.

**왜 작업 세션은 Opus 인가.** Fable 의 가치는 아직 정해지지 않은 것을 정하는 데 있다. 계획 문서가 경로·단계·검증까지 확정해 뒀다면 작업 단계의 판단은 "계획대로 되고 있는지"와 "예외 처리"뿐이고 Opus 로 충분하다. 단가도 절반이다.

### 작업 세션의 계획 이탈 금지

계획이 아무리 꼼꼼해도 작업 중 계획에 없는 판단이 필요해지는 순간이 온다. 그때 부모가 즉석에서 설계 결정을 내리면 "판단은 최상위 모델" 원칙이 조용히 무너진다.

- **구조·인터페이스·범위에 영향을 주는 판단** → 임의 결정하지 않고 **멈추고 사용자에게 보고**한다. 사안이 크면 계획 세션으로 되돌아가 계획을 갱신한 뒤 재개한다
  - 보고는 `.agent-shared.md` 끝에 `[QUESTION from=<세션id>]` 표지로 시작하는 블록(맥락 / 질문 / 선택지 / 작업 세션 의견)을 append 하고 멈춘다. **터미널 출력만으로 끝내지 않는다** — 계획 세션이 그 표지를 감시한다
- **작은 판단**(변수명, 오류 메시지 문구 등) → 부모가 처리한다

### 계획 세션도 마찬가지 — 제안한 규칙은 명시 승인 뒤에 반영

계획 세션이 **스스로 만든** 세부 규칙·구현 방식(필터 규칙, 저장 방식, 매칭 키 등)을 제안했으면, 사용자가 **그 안을 고르는 문장**("그렇게 해", "1번으로")을 말한 뒤에만 계획 문서를 고치고 작업 세션에 전달한다.

- "이 부분 반영되는지 체크해줘", "확인해줘" 는 **점검 요청**이지 승인이 아니다 — 답하고 멈춘다
- 사용자가 **직접 지시한 변경**("라인도 수정 가능하게 해줘")은 그 지시가 곧 승인이므로 바로 반영해도 된다. 게이트는 세션이 만들어 낸 세부 사항에 걸린다
- **작업이 시작된 뒤 사용자가 던진 추가 요청도 예외가 아니다.** 요청을 받아 세부 규칙·방식을 내가 정했으면 그 세부는 승인 대상이다. 사용자가 말을 던져 놓고 다음 말이 없으면 임의로 진행하지 말고 **"이 안으로 진행할까요?" 로 승인을 재요청하고 대기**한다. 승인된 것만 진행한다
- 승인 없이 전달해 버렸으면 되돌리려 하지 말고 작업 세션에 **보류**를 보내고 사용자에게 보고한다

### 계획 문서 필수 절 3개

계획 문서에는 아래 세 절이 **반드시** 있다. 없으면 핸드오프하지 않는다.

- **스펙 추적표** — 아래 "플랜 작성 전 코드 추적 게이트" 1번의 표. 스펙 조항 한 행마다 코드 근거·사용처·판정·담당 Task·확인 테스트.
- **영향 범위** — 저장소에 영향 지도(예: `docs/impact.md`)가 있으면 이 변경이 닿는 행(테이블·컬럼·엔드포인트·모듈·값 집합·성질)을 **그대로 복사**한 표. 빼는 칸이 있으면 이유를 적는다. 사용자는 계획 검토 때 이 표로 범위 축소를 잡는다.
- **변경 요청 로그** — 계획 승인 뒤 들어온 요청마다 한 행. `상태: 논의 중 / 승인 / 전달`. **`승인` 이 없는 항목은 작업 세션에 보내지 못한다.** 사용자가 요청을 던지고 다음 말이 없으면 "이 안으로 진행할까요?" 로 승인을 재요청하고 대기한다.

### 플랜 작성 전 코드 추적 게이트

스펙이 승인되면 바로 플랜을 쓰지 않는다. **스펙의 각 조항이 지금 코드에서 사용자가 원하는 결과로 실제 이어지는지 먼저 코드로 추적**하고, 그 결과로만 플랜을 쓴다. "이렇게 하면 적용되겠지" 로 쓴 Task 는 금지다. 스펙과 플랜 사이의 오차(조항 누락·의미 변형·부정 조건 소실·추정값 확정·승인 없는 결정 추가)가 반복 재수정의 주원인이었기 때문이다(2026-10-08 스펙↔플랜 4쌍 대조).

1. **조항 단위 추적표** — 스펙의 결정·규칙·예외("~이면 안 된다")·수치·검증/확인 조항·미결 사항을 **한 행씩 전부** 뽑는다. 행마다 다음 칸을 채운다.
   - **현재 동작** — `file:line` 과 실제 시그니처. 기억·유추로 쓰지 않는다. 하위가 원문을 읽고 짧은 인용과 함께 돌려준다
   - **사용처 전수** — 바꿀 값·심볼·하드코딩 열거(값 목록, 문구, 주석, 테스트 스텁·시드)를 grep 으로 닫은 목록과 그 grep 명령. 화면 단위로 파일을 고르지 않는다
   - **판정** — 그 변경으로 사용자가 원하는 결과가 실제로 나오는가: `예 / 아니오 / 불명` 과 근거
   - **담당 Task·확인 테스트** — 부정 조건·예외는 테스트 케이스와 1:1
   추적 노동은 하위(`researcher` / `codex exec --profile research`)에 맡기되 원문 근거를 받는다. `아니오`·`불명` 행은 부모가 직접 검증한다.
2. **실측이 필요한 전제는 플랜 전에 잰다** — 데이터 지연, 외부 프로그램 출력값, 실제 렌더 폭처럼 코드만으로 알 수 없는 것은 dev DB·로그·브라우저로 먼저 확인한다. "구현 후 dev 에서 확인" 으로 넘기지 않는다. 잴 수 없으면 3번으로 간다.
3. **애매하거나 확정 안 된 것은 사용자에게 결정을 재요청한다** — `아니오`·`불명` 행, 스펙이 정하지 않은 분기, 스펙의 미결 사항, 추정으로만 채울 수 있는 값을 플랜에서 임의로 메우지 않는다. 한 번에 하나씩(§11) 선택지와 함께 묻고, 결정이 나면 **스펙을 먼저 고친 뒤** 플랜에 반영한다.
4. **플랜이 새로 정한 것은 승인 대상** — 구현 수단을 넘는 결정(API 필드·계약, 화면 표기, 범위 밖 리팩터, 새 엔드포인트, 새 타입·계층 구조)을 플랜이 추가하면 "플랜 신규 결정" 목록과 변경 요청 로그에 `논의 중` 으로 올리고 승인 뒤에만 넘긴다.
5. **Task 는 추적표 행에서만 나온다** — 모든 Task 에 근거 행 번호를 단다. 추적표에 없는 변경은 Task 로 쓰지 않는다. Task 가 붙지 않은 스펙 행이 있으면 플랜은 미완성이다. 검증·확인 조항은 마지막 검증 Task 의 체크박스로 조항 번호와 함께 옮긴다.
6. **변경은 본문을 고친다** — 승인 뒤 바뀐 결정은 해당 Task 본문과 추적표를 고친다. 문서 끝에 주의문·추가 라운드로 덧붙이지 않는다. 옛 값이 문서에 남아 있으면 안 된다.
7. **핸드오프 직전 재대조** — 현재 HEAD(와 미커밋 변경)에 대고 추적표의 `file:line`·시그니처를 다시 확인한다. 플랜 작성 뒤 들어온 다른 작업으로 낡은 부분을 고치고, 기준 커밋을 하나로 맞추고, 문서 깨짐(헤더·백틱·경로)을 점검한다.

**핸드오프 조건**: 추적표 빈 칸 0, `아니오`·`불명` 0(전부 사용자 결정으로 해소), 스펙 미결 사항 0, 플랜 신규 결정 전부 `승인`. 하나라도 남으면 핸드오프하지 않는다.

### 리뷰는 부모가 직접

`reviewer` 서브에이전트도 Opus 5 이지만 **기본은 부모의 직접 검수**다. 같은 모델인데 **부모가 맥락 우위**를 갖고(서브에이전트는 격리 컨텍스트라 계획과 diff 를 처음부터 다시 읽어야 한다), **리뷰는 원문을 봐야 판단이 성립**한다 — 요약된 diff 로 하는 리뷰는 리뷰가 아니므로 여기서는 격리가 손실이다. **무단 커밋·머지 검출은 항상 부모가 직접** 한다(§3).

예외: 변경 규모가 매우 커서 부모가 전체 diff 를 읽으면 컨텍스트가 넘칠 때만 영역별로 `reviewer` 에 나눠 위임하고 **부모가 종합 판단**한다.

### 서브에이전트 (세션 안에서 쓰는 도구)

| 에이전트 | 모델 | effort | 용도 |
|---|---|---|---|
| `researcher` | `claude-sonnet-5` | medium | **조사 전용.** 넓게 훑어 결론만 요약 반환. 계획 세션의 주력 |
| `planner` | `claude-fable-5-1` | low | **대화가 필요 없는 단발 전략 수립**(예: `:AgentMerge` 2단계). 사용자와 오래 주고받는 계획은 Fable 세션이 직접 |
| `planner-fallback` | `claude-opus-5` | medium | `planner` 가 사용량 한도로 막혔을 때 이어받기(§5) |
| `implementer` | `claude-sonnet-5` | medium | 계획 문서를 근거로 코드 작업 |
| `reviewer` | `claude-opus-5` | medium | 큰 변경의 영역별 분할 검수 전용 |

`planner`·`planner-fallback`·`researcher`·`reviewer` 에는 **Edit/Write 를 부여하지 않는다** — 규칙이 아니라 도구 권한으로 차단한다. `reviewer` 에는 **Bash 도 주지 않는다**: Edit/Write 를 빼도 셸이 있으면 `echo ... > file` 로 우회 쓰기가 가능하기 때문이다. 무단 커밋 검출은 어차피 부모의 몫이다(§3).

### 계획 세션은 하위 모델을 자유롭게 골라 쓴다

**Fable 은 서브에이전트를 제한 없이 사용한다.** 조사만 시키는 것이 아니라 **작업 난도에 맞는 모델을 스스로 골라 부여**한다. 판단은 계획 세션이 하고 노동은 하위가 한다는 원칙은 그대로다.

수단은 **모델 오버라이드**다 — 에이전트를 새로 만들 필요가 없다. Agent 도구의 `model` 파라미터(`sonnet`·`opus`·`haiku`·`fable`)가 에이전트 정의의 `model` frontmatter 보다 **우선**한다.

| 작업 성격 | 모델 | 예 |
|---|---|---|
| 단순 열거·패턴 매칭 | `haiku` | "이 심볼을 쓰는 파일을 전부 찾아라" |
| 일반 조사 (기본) | `sonnet` | "이 규칙이 어디서 깨지는지 찾아라" |
| 깊은 분석·설계 판단이 섞인 조사 | `opus` | "이 두 모듈의 결합도를 평가하고 분리 가능 지점을 찾아라" |

**기본은 `sonnet`** 이고 올리는 것은 예외다. Opus 를 남발하면 하위 위임으로 아끼려던 비용이 도로 늘어난다. **하위에 Fable 을 부여하지 않는다** — 최상위가 둘이 되면 역할 분리의 의미가 사라지고 비용만 배가된다.

여러 조사가 서로 독립적이면 **한 번에 여러 하위를 띄워 병렬로** 돌린다. 조사는 파일을 쓰지 않으므로 서로 간섭하지 않는다.

**토큰 비용 상한.** Fable 5.1 은 Sonnet 5 의 5배 단가다. Fable 의 effort 는 **`low` 를 기본**으로 하고, 품질이 부족할 때만 `medium` → `high` 까지 올린다. **`xhigh`·`max` 는 금지**한다. 품질이 부족하면 effort 를 올리기보다 **입력(브리핑·설계문서)을 더 충실하게** 만들거나 `researcher` 에게 조사를 더 시킨다.

**교차 벤더 심층 검수.** Claude 쪽에서 **매우 큰 변경**을 만든 뒤에는 `codex --profile deep-review`(`gpt-6-astra`, read-only)가 독립적으로 검수한다. 같은 계열 모델은 사각지대를 공유하므로 벤더를 바꾸면 다른 지적이 나온다. astra 가 검수 중 한도에 걸리면 `codex --profile deep-review -m gpt-6.1-sol` 로 이어가고 astra 가 어디까지 봤는지 `.agent-shared.md` 에 적는다. astra 는 비싸므로 변경이 정말 클 때만 쓴다.

### Codex 세션 (Codex 가 이 파일을 읽을 때)

**Codex 에는 정의형 서브에이전트가 없다.** `codex agents` 는 실행 중인 세션 목록 조회일 뿐이고, 자동 위임은 `ultra` reasoning 에만 있는데 그것은 아래에서 금지했다. 하위 작업은 **부모 세션에서 `codex exec` 를 셸로 호출**해 대신한다 — 별도 프로세스·격리 컨텍스트로 돌고 stdout 으로 결과만 반환하므로 원문이 부모 컨텍스트에 쌓이지 않는다.

| 역할 | 프로필 | 모델 | 샌드박스 |
|---|---|---|---|
| **계획 세션 (부모)** | `codex --profile plan` | `gpt-6.1-sol` | 문서만 쓰기 (`plan-docs`) |
| 계획 폴백 | `codex --profile plan-fallback` | `gpt-6.1-sol` | 문서만 쓰기 (`plan-docs`) |
| **작업 세션 (부모)** | `codex --profile work` | `gpt-6.1-sol` | workspace-write |
| 하위 조사 | `codex exec --profile research` | `gpt-6-luna` | read-only |
| 하위 구현 | `codex exec --profile build` | `gpt-6-luna` | workspace-write |
| 분할 검수 | `codex --profile review` | `gpt-6.1-sol` | read-only |
| **교차 검수** | `codex --profile deep-review` | `gpt-6-astra` | read-only |

**세션은 `plan` 또는 `work` 중 하나로 연다.** `research`·`build` 는 그 세션 안에서 `codex exec` 로 호출하는 하위 작업용이다. `codex exec` 하위 호출의 반환 보고도 한국어다(§7). 핸드오프(§8)에서 `'agent': 'codex'` 는 `codex --profile work` 로, `'agent': 'claude'` 는 `claude --model opus` 로 뜬다.

**계획 세션은 하위 위임을 제한 없이 사용한다.** 작업 난도에 맞는 모델을 스스로 골라 `-m` 오버라이드로 부여한다 — 예: `codex exec --profile research -m gpt-6.1-sol "깊은 분석이 필요한 조사"`. 일반 조사는 프로필 기본값 `gpt-6-luna`, 깊은 분석·설계 판단이 섞인 조사는 `gpt-6.1-sol`. **기본은 프로필 값(`luna`)** 이고 올리는 것은 예외다. **하위에 `astra` 를 부여하지 않는다.**

**Codex 고유 한계:** 프로필로는 도구 권한을 세분화할 수 없다. Claude Code 의 서브에이전트처럼 "편집 도구를 아예 주지 않는" 방식이 불가능하므로 경로 단위 권한 프로필로 막는다. `plan`·`plan-fallback` 은 `default_permissions = "plan-docs"` — 전체 읽기 + 작업 루트의 `docs/`·`.agent-shared.md` 만 쓰기다. 계획 문서는 승인 없이 쓰고, 코드 경로에 쓰려 하면 샌드박스가 거부해 사용자 승인을 받아야 한다(2026-10-08 실측: `docs\` 쓰기 성공, `backend\`·`frontend\`·루트 신규 파일 거부). 이 프로필에는 `sandbox_mode` 를 넣지 않는다 — 함께 있으면 `sandbox_mode` 가 이기고 권한 프로필이 무시된다. 그래도 규칙 의존도가 Claude 쪽보다 높으니 §1 을 엄격히 지킨다.

**`gpt-6-astra` 는 토큰 사용량이 매우 크다.** 그래서 `plan` 프로필은 2026-10-08 부터 `gpt-6.1-sol`(reasoning `medium`)을 쓰고, astra 는 `deep-review` 에만 남는다. `deep-review` 프로필의 `model_reasoning_effort` 는 **`low` 를 기본**으로 하고, 부족할 때만 **`medium` 까지** 올린다. **`high`·`xhigh`·`max`·`ultra` 는 금지**한다. 특히 **`ultra` 는 "Maximum reasoning with automatic task delegation"** 이라 자동 작업 위임으로 파생 세션을 만들어 비용이 배가될 수 있다 — 금지 목록에서 가장 위험하다. astra 의 제작사 기본값도 `low` 다. 품질이 부족하면 reasoning 을 올리기보다 입력을 더 충실하게 만들거나 `codex exec --profile research` 에게 조사를 더 시킨다. 하위 모델(`sol`·`luna`)에는 이 상한을 적용하지 않고 `medium` 을 기본으로 둔다.

## 3. 무단 커밋·머지 검출

규칙에도 오류로 커밋·머지가 발생할 수 있다. git 은 되돌릴 수 있으므로 **발생 사실을 놓치지 않는 것**이 관건이다.

리뷰할 때 **매번** 다음을 점검해 보고한다:

```bash
git log --oneline -20
git log --merges --oneline -10
git status
```

- 작업 시작 시점의 HEAD 와 현재 HEAD 를 비교한다
- 사용자가 지시하지 않은 커밋·머지가 있으면 **커밋 해시·시각·대상 브랜치와 함께 즉시 보고**한다
- `-a` 계열이 본선에 섞여 들어갔는지도 함께 점검한다
- 되돌리기 명령은 실행하지 않는다 (git 변경 규칙 적용). 사용자가 판단한다

## 4. 작업 완료 보고

작업이 끝나면 **매번** 완료 내용을 간단히 정리해 보여준다.

포함할 것:
- 완료된 작업 목록 (항목별로 짧게)
- 변경된 파일 목록 (경로)
- 미완료·보류 항목과 그 이유 (없으면 생략)
- 실패한 검증 — 테스트·빌드가 실패했으면 **숨기지 않고 결과 그대로**
- **영향 범위 표의 칸별 처리 여부** — 계획의 영향 범위 표를 그대로 가져와 칸마다 `처리 / 해당 없음(이유) / 보류(이유)` 를 적는다
- **갱신한 문서와 새 `기준:` 커밋** — 문서 경로마다 갱신 전·후 `기준:` 해시

**진행 보고 형식**(작업 중간 보고 포함): 총 Task 수 / 현재 Task 번호 / 병렬 갈래가 있으면 갈래별 진행 Task 를 항상 적는다.

포함하지 않을 것:
- 커밋·머지·push 언급 (§1)
- 장황한 서술 — 표나 목록으로 짧게

## 5. 계획 인수인계 (사용량 한도 대비)

`fable`(Claude)·`sol`(Codex 계획 세션)은 사용량 한도에 걸릴 수 있다. 그때 한 등급 아래 모델이 **앞선 논의를 이어받아** 계획을 완성해야 한다.

| 등급 | Claude | Codex |
|---|---|---|
| 1차 | `claude-fable-5-1` (`planner`) | `gpt-6.1-sol` (`--profile plan`) |
| **폴백** | **`claude-opus-5`** (`planner-fallback`) | **`gpt-6.1-sol`** (`--profile plan-fallback`) — 1차와 같은 모델이라 한도 시에는 사실상 최후 등급으로 간다 |
| 최후 | `claude-sonnet-5` | `gpt-6-luna` |

### 이어받기가 가능하려면 — 점진적 기록이 전제

컨텍스트는 세션과 함께 사라진다. 중단 시점에 **파일에 남아 있는 것만** 인수인계된다. 따라서 계획을 세우는 동안:

- **설계·계획 문서를 한 번에 완성하지 않고 처음부터 파일로 만들어 점진적으로 갱신한다.** 조사 결과가 나오는 대로 즉시 기록한다
- 문서 머리에 **`상태:`** 를 유지한다 — 예: `작성 중 (§2 조사 완료, §4 작성 중)` / `설계 확정`
- **`## 미결 사항`** 절에 사용자에게 물을 것과 아직 판단하지 못한 것을 남긴다. 해소되면 지운다
- **조사로 확인한 사실은 명령과 출력값까지 남긴다** — 다음 모델이 같은 조사를 반복하지 않도록
- 사용자와 확정한 결정은 **즉시** 결정 요약 표에 추가한다. "나중에 정리"하지 않는다

### 이어받을 때

1. 설계·계획 문서 **전문**과 `.agent-shared.md` 를 읽는다
2. `상태:` 와 `## 미결 사항` 으로 이어갈 지점을 파악해 **사용자에게 확인**한다
3. **이미 확정된 결정을 다시 묻지 않는다.** 되묻는 것은 인수인계 실패다
4. 앞선 결정을 **뒤집지 않는다.** 모순을 발견하면 조용히 고치지 말고 보고한다
5. 폴백 모델이 작성한 절은 문서에 명기한다 — `작성: ... (§4~ Opus 5 — Fable 사용량 한도로 폴백)`

### 복잡도 경고 — 하위 모델로 잇기 어려운 경우

폴백 모델은 이어받기 전에 자체 평가하고, 아래에 해당하면 **작업 전에 경고**한다:

- **문서에 남지 않은 맥락에 의존하는 부분** — 추측하면 앞선 결정을 뒤집는다
- 여러 서브시스템에 걸친 상호 의존 결정
- 되돌리기 어려운 결정 (데이터 마이그레이션, 외부 계약, 배포 구조)
- 조사 범위가 넓어 근거 수집 자체가 무거운 경우
- 앞선 결정 간에 모순이 보이는 경우

경고에는 **무엇이 왜 위험한지 + 그래도 진행할 때의 위험 + 대안**(한도 회복 후 상위 모델로 재개 / 그 부분만 사용자가 직접 결정 / 범위를 쪼개 안전한 부분만)을 담는다. 경고 후 사용자가 진행하라고 하면 진행한다.

## 6. 작업 분할 전략 — 서로 영향을 주는 작업

계획은 병렬로 자유롭게 세워도 되지만(§0), **작업은 서로 영향을 줄 수 있다.** 여러 작업을 어떻게 배치할지는 **계획 단계에서 판단한다.**

### 1단계: 영향 여부를 먼저 판정한다

- **파일 겹침** — 같은 파일을 고치는가
- **인터페이스 의존** — A 가 만드는 함수·API·상태를 B 가 쓰는가
- **동일 모듈·동일 화면** — 파일은 달라도 같은 동작 경로에 놓이는가
- **공용 자원** — DB 스키마, 설정 파일, 공통 유틸, i18n 키

`researcher` 에게 조사를 시켜 근거를 모은 뒤 계획 세션이 결정한다.

### 2단계: 영향이 없으면 자유롭게 병렬

겹치는 것이 없으면 각각 worktree 로 갈라 동시에 진행한다.

### 2단계': 영향이 있으면 두 전략 중 하나

**둘 다 "영향 확인"을 반드시 포함한다. 어디서 확인하는지만 다르다.**

| 전략 | 흐름 | 유리한 경우 | 비용 |
|---|---|---|---|
| **① 순차 + 작업 후 확인** | 작업 1 완료 → **영향 범위 확인**하고 필요하면 반영 → 작업 2 시작 | 의존이 강하다 / 영향 범위가 불명확하다 / 충돌 해결이 어려운 영역이다 | 뒤 작업이 대기한다 |
| **② 병렬 worktree + 머지 시 확인** | 각각 격리 작업 → **머지할 때 영향·충돌 확인**(`:AgentMerge`) | 파일이 거의 겹치지 않는다 / 독립 검증이 가능하다 / 작업이 길어 대기 비용이 크다 | 머지 조정이 필요하다 |

**애매하면 ①을 고른다.** 순차는 늦을 뿐이지만, 잘못된 병렬은 통합 시점에 두 작업을 모두 다시 봐야 한다.

### ①의 "영향 확인"이란

작업 1 이 끝난 뒤 확인하고, 필요하면 작업 2 의 계획을 갱신한다:

- 작업 1 이 바꾼 인터페이스·시그니처·상태를 작업 2 가 전제하고 있었는가
- 삭제된 심볼을 작업 2 계획이 참조하는가 (`grep` 으로 확인)
- 작업 1 로 인해 작업 2 의 일부가 이미 해소되었거나 불필요해졌는가

**계획을 갱신해야 하면 계획 세션으로 되돌아간다**(§2 계획 이탈 금지). 작업 세션이 임의로 작업 2 의 설계를 바꾸지 않는다.

### 계획 문서에 남길 것

작업이 둘 이상이면 **어느 전략을 골랐는지와 근거**를 계획 문서에 기록한다. ②를 골랐다면 **예상 충돌 지점**도 함께 적는다.

### 한 계획 안의 프론트·백엔드 병렬 — 기본이 병렬

위 ①②는 **서로 다른 작업 항목**을 어떻게 배치하느냐의 문제다. 그와 별개로 **한 계획 안에** 프론트엔드와 백엔드 Task 가 함께 있으면 **기본이 병렬**이다 — worktree 를 가르지 않고, 작업 세션이 같은 작업 트리에서 갈래별 `implementer` 를 동시에 띄운다.

- **갈래**: 백엔드 / 프론트엔드(크면 프론트 A·B 로 더 분할) / 문서. 문서 갈래는 **코드 갈래가 합류한 뒤** 착수한다 — 코드가 정본이라 최종 상태를 대조해야 한다.
- **테스트 코드는 별도 갈래로 떼지 않는다.** 계획이 Task 마다 TDD 순서(실패 테스트 → 구현 → 통과)로 짜여 있어, 테스트만 분리하면 같은 파일을 두 에이전트가 동시에 쓴다. 각 구현 갈래가 자기 테스트를 함께 쓴다.
- 갈래가 병행할 수 있도록 **계획 문서에 갈래 경계 계약**(API 응답 필드·시그니처·상태 키)을 명시한다. 프론트는 그 계약을 전제로 mock 으로 먼저 확인한다.
- **ko/en 로케일 파일은 프론트 갈래 하나가 단독 소유.** 백엔드 갈래는 `ErrorCode` 추가 시 `error.<ENUM>` 키 목록만 넘긴다. 각 갈래에 **접근 금지 폴더**를 명시해 파일 겹침을 막는다.
- 합류 후 최종 검증(백엔드 테스트·E2E·빌드)은 순차로 한 번 돌리고 결과 원문을 보고한다(§4 진행 보고 형식 — 총 Task 수/현재 번호/갈래별 진행).

### 최종 검수 주체 — 2단계

| 상황 | 검수 |
|---|---|
| **기본** — 단일 갈래, 또는 프론트·백엔드 2갈래 정도 | 작업 세션 부모(Opus)가 직접(§2 "리뷰는 부모가 직접") |
| 병렬 갈래 **3개 이상** / **DB 스키마·API 계약 변경** 포함 / 변경 규모가 매우 큼 | 작업 세션 검수 통과 후 **계획 세션(Fable)이 최종 검수를 한 번 더** |

Fable 최종 검수는 **원문을 직접 다 읽지 않는다**(단가 문제 — 원문이 컨텍스트에 쌓이면 매 턴 재청구). diff 를 영역별 `reviewer`(Opus)에 나눠 읽히고 요약을 받되, 다음 세 가지는 Fable 이 직접 판단한다: **갈래 경계 계약 정합**(백엔드 응답 ↔ 프론트 소비 ↔ 테스트 전제 ↔ E2E mock), **스펙 핵심 결정 준수**, **문서 정합**. 무단 커밋·머지 점검(§3)은 검수 주체가 누구든 직접 한다.

검수 순서는 **코드 → 문서**다. ① 코드 갈래 합류 즉시 1차 코드 검수(문서 갈래와 병행) → ② 잔여 코드 Task 완료 후 2차 → ③ 문서 작성이 끝나면 코드 검수에서 확정한 동작을 기준으로 문서 검수. 문서를 코드보다 먼저 보지 않는다.

## 7. 언어 설정

**사용자가 읽는 모든 것은 한국어다. 예외는 없다.**

- 대화·답변·질문
- 진행 상황 보고, 작업 완료 보고
- 오류 메시지 설명, 기술 용어 해설
- 계획·설계 문서, 코드 주석
- **서브에이전트의 반환 보고도 한국어다** — `researcher`·`implementer`·`reviewer`·`planner` 전부 해당한다. 격리 컨텍스트라고 예외가 아니다
- 표·목록·제목 등 출력의 모든 부분

**번역하지 않고 원문 그대로 두는 것:**

- 코드 식별자(변수·함수·클래스명), 파일 경로, 명령어
- 명령 실행 결과와 로그 원문 — 다만 그 **설명**은 한국어로 쓴다
- 라이브러리·도구의 고유명사

**예외는 규약 파일 자체뿐이다.** `CLAUDE.md`·`AGENTS.md` 는 영어로 쓰는 프로젝트가 있으므로 해당 프로젝트의 규칙을 따른다. 사용자가 직접 읽는 문서가 아니기 때문이다.

## 8. 작업 세션 자동 핸드오프 (nvim 안에서만)

계획이 끝나고 사용자가 **"작업 시작"이라고 말했을 때만** 아래를 수행한다. 계획 문서를 다 썼다는 이유로 자동으로 시작하지 않는다.

**조건:** 환경변수 `$NVIM` 이 있을 때만 가능하다(nvim 터미널 안에서 실행 중이라는 뜻). 없으면 이 절은 적용되지 않으며, 사용자에게 직접 작업 세션을 열어달라고 요청한다.

```bash
nvim --headless --server "$NVIM" --remote-expr "v:lua.AgentHandoff({'agent': 'claude', 'session': 'work', 'plan_doc': '<계획 문서 경로>', 'worktree': '<작업 폴더>', 'strategy': '<순차/병렬과 담당 범위>'})"
```

- `--headless` 를 **반드시** 붙인다. 없으면 반환값이 터미널 제어 문자로 깨진다
- 인자는 **작은따옴표**를 쓴다. 큰따옴표는 셸을 거치며 소실된다
- `agent` 는 `'claude'` 또는 `'codex'`
- 반환값이 `OK id=...` 이면 성공, `FAIL: ...` 이면 사유를 사용자에게 그대로 보고한다

**함께 넘길 것:**

| 인자 | 내용 |
|---|---|
| `plan_doc` | 계획 문서의 전체 경로 |
| `worktree` | §6 에서 정한 작업 폴더. 새로 만들었으면 그 경로 |
| `strategy` | 순차/병렬 여부. 병렬이면 이 세션이 맡을 범위 |
| `rules` | 생략하면 기본 문구가 들어간다 — "계획 이탈 금지, 커밋·머지 언급 금지, push 금지" |

**핸드오프 후에는 계획 세션이 작업에 관여하지 않는다.** 작업은 새로 뜬 세션이 한다.

### 핸드오프 뒤 감시·전달은 계획 세션이 직접 한다 — 모든 세션 공통

작업 세션은 별도 터미널이라 알림이 오지 않지만, **사용자에게 "끝나면 알려 달라", "작업 세션에 전달해 달라"고 부탁하지 않는다.** nvim 에이전트 허브의 원격 호출로 스스로 한다(`$NVIM` 이 있을 때).

| 목적 | 명령 |
|---|---|
| 세션 목록 조회 | `nvim --headless --server "$NVIM" --remote-expr "luaeval(\"vim.json.encode(require('config.agent.terminal').entries())\")"` → `[{id, name, branch, cwd, …}]` |
| 작업 세션에 메시지 주입 | `nvim --headless --server "$NVIM" --remote-expr "luaeval(\"require('config.agent.terminal').send(<id>, '<본문>')\")"` — 개행이 붙어 그대로 실행된다. 본문은 작은따옴표 안, `'` 는 `''` 로 |

- **질문 감지**: 완료 감시와 함께 `.agent-shared.md` 의 `[QUESTION]` 표지를 감시한다. 표지가 오면 맥락을 검수해 사용자에게 설명·질문하고, 결정을 받아 `send()` 로 작업 세션에 돌려준다. 작업 세션은 답이 올 때까지 대기한다.
- **완료 감지**: 작업 세션이 완료 보고 끝에 `[AGENT-DONE]` 을 찍으면 훅이 세션을 닫아 목록에서 사라진다. 핸드오프 직후 Monitor(20초 폴링)로 그 id 가 사라지는 것과 `.agent-shared.md` 새 줄을 함께 감시하고, 사라지면 완료 보고·검증 원문·무단 커밋 점검을 확인해 사용자에게 알린다. `.agent-shared.md` 만 보면 작업 세션이 마지막에만 쓰므로 늦다.
- **플랜 변경 전달**: 핸드오프 뒤 사용자 지시로 플랜에 Task 를 추가·수정했으면 `send()` 로 "플랜 §X 추가됨, 다시 읽어라"를 **직접** 보낸다. 사용자가 옮겨 적게 하지 않는다.
- 이 규칙은 Claude·Codex 계획 세션 모두에 적용된다(Codex 는 같은 셸 명령을 쓴다).

## 9. 세션 간 맥락 공유 (`.agent-shared.md`)

Claude Code 와 Codex 는 실시간으로 컨텍스트를 공유할 수 없다 — 어느 쪽도 진행 중인 세션에 외부에서 끼워넣는 API 를 열지 않는다. 대신 **파일을 경유**한다.

- 모든 세션은 **시작할 때 `.agent-shared.md` 를 읽고**, **끝날 때 덧붙인다**
- Claude↔Claude, Claude↔Codex, Codex↔Codex 모두 이 파일을 경유한다
- 기록할 것: 무엇을 작업했는지, 어떤 파일을 건드렸는지, 다른 세션이 알아야 할 결정, 미해결 항목
- 이 파일은 gitignore 된다 — 이력이 아니라 로컬 작업 상태다
- **짧게, 날짜와 함께** 쓴다. diff 전체를 붙이지 않는다
- 파일이 없으면 만들지 않아도 된다. 쓸 내용이 생겼을 때 만든다

## 10. `:AgentMerge` — 머지 조정 (2~4단계)

nvim 의 `:AgentMerge` 가 1단계 브리핑을 만들어 이 세션에 넘긴다. **2단계부터가 이 세션의 몫이다.**

### 게이트 — 반드시 지킨다

브리핑을 받으면 **2단계(전략 판단)까지만** 하고 **전략 문서를 보여주며 멈춘다.** 거기서 턴을 끝낸다.

**3단계로 넘어가는 조건은 하나뿐이다** — 사용자가 **자기 입으로 머지를 지시하는 문장을 타이핑**하는 것. 그 전에는 어떤 이유로도 머지하지 않는다.

**다음은 모두 위반이다:**

- "이제 머지할까요?" / "3단계로 넘어갈까요?" / "진행할까요?" — **묻는 것 자체가 금지**다
- 사용자가 "좋네", "괜찮아 보여", "알겠어" 라고 한 것을 지시로 해석하는 것
- 브리핑에 **충돌이 없으니** 안전하다고 판단해 바로 머지하는 것
- 전략 문서를 내면서 **같은 턴에** 머지까지 실행하는 것
- 사용자가 앞서 다른 머지를 승인했으니 이번에도 승인한 것으로 보는 것 — **승인은 매번 새로 받는다**
- `git merge` 를 실행할 도구·권한이 있다는 이유로 실행하는 것 — **도구가 있다는 것과 권한이 있다는 것은 다르다**

지시가 애매하면 **멈추고 확인한다.** "머지해"인지 아닌지 판단이 서지 않으면 그것은 지시가 아니다.

**3단계를 시작하기 직전에 스스로 점검한다:**

1. 사용자가 타이핑으로 머지를 지시했는가 — 아니면 중단
2. 대상에 `-a` 계열이 섞이지 않았는가 — 섞였으면 중단
3. 지금 `git status` 가 깨끗한가, 현재 브랜치가 브리핑의 target 과 같은가 — 다르면 중단하고 보고

**4단계가 끝나면 push 직전에 멈춘다.** push 는 사용자만 한다. 머지 후 추가 커밋도 하지 않는다.

### 머지 후 정리 — 승인 없이 자동 수행

4단계 검수(양쪽 기능 테스트 통과 + 무단 커밋 점검)가 끝나면 머지를 수행한 세션이 **바로 이어서** 아래를 실행한다. 사용자에게 묻지 않는다 — "작업 세션 창이 계속 늘어나기만 한다" 는 문제를 없애기 위한 결정이다.

1. **작업 세션 창 닫기** — 머지된 worktree 로 핸드오프됐던 작업 세션을 닫는다(`$NVIM` 이 있을 때):
   ```bash
   nvim --headless --server "$NVIM" --remote-expr "v:lua.AgentDone({'cwd': '<worktree 경로>'})"
   ```
   nvim 이 그 터미널에 `/exit`(Codex 는 `/quit`)를 보내고, 프로세스가 끝나면 창과 버퍼를 지운다(`terminal.lua` `M.done`). 반환값 `OK closing …` 을 확인한다. `FAIL: 해당 세션 없음` 이면 이미 닫힌 것이므로 넘어간다. **같은 cwd 의 세션이 둘 이상이면 `FAIL: 같은 cwd 의 세션이 여럿` 을 돌려주고 아무것도 닫지 않는다**(cwd 첫 매치로 잘못된 세션이 닫히는 것을 막기 위함). 그때는 `entries()` 로 id 를 확인해 `AgentDone({'id': N})` 으로 지정한다. 작업 세션의 Stop 훅은 자기 조상 PID 를 `pids` 로 넘겨 자기 세션만 닫는다.
2. **worktree 제거** — 먼저 그 worktree 에서 `git status --short` 를 확인한다(`--force` 는 gitignore 된 `CLAUDE.md` 사본·스크래치 파일 같은 추적되지 않는 파일까지 지우므로 남길 것은 먼저 옮긴다). 세션이 끝난 뒤(몇 초 대기) `git worktree remove --force <경로>`. 폴더가 잠겨 있으면(`Permission denied`/`resource busy`) 아직 그 폴더를 쓰는 프로세스가 있다는 뜻이다 — 강제로 지우지 말고 사용자에게 보고한다.
3. **브랜치 삭제** — `git merge-base --is-ancestor <브랜치> <통합 브랜치>` 가 참인지 확인한 뒤 `git branch -D <브랜치>`(`-d` 는 upstream 이 main 이라 거부된다). 참이 아니면 삭제하지 않고 보고한다.

**대상은 임시 병렬 worktree(`<repo>/worktrees/<name>`)만이다.** 고객사 배포 폴더(`rbm-hotfix-*`)와 그 브랜치(`hotfix/*`)는 이 절차의 대상이 아니며 절대 지우지 않는다.

**작업 세션이 스스로 닫히는 경로도 있다.** 작업 세션이 완료 보고 마지막 줄에 `[AGENT-DONE]` 을 찍으면 Claude `Stop` 훅 / Codex `notify`(`~/.claude/hooks/agent-done.js`)가 그 세션을 닫는다 — nvim 안이면 위 `AgentDone` 을 대신 호출하고, 밖이면 프로세스를 종료한다. 이 마커는 **계획에 있는 작업이 전부 끝나고 검증까지 통과했으며 사용자에게 물을 것이 남지 않았을 때만** 찍는다. 계획·조사 세션은 절대 찍지 않는다.

**훅은 `AGENT_SESSION_ROLE=work` 인 세션만 닫는다**(계획 세션이 마커 문자열을 인용만 해도 스스로 닫히는 것을 막기 위함). 핸드오프(`handoff.lua`)·메뉴(`menu.lua`)·런처(`launcher.lua`)가 세션을 띄울 때 `terminal.spawn` 의 `env` 로 역할을 넣어 준다. 그래서 계획 세션은 마커를 인용해도 닫히지 않지만, **nvim 밖에서 직접 띄우는 작업 세션은 `AGENT_SESSION_ROLE=work` 를 설정하고 실행해야** 자동 종료가 동작한다. 이 변수 없이 떠 있던 기존 작업 세션은 마커를 찍어도 닫히지 않으므로 `AgentDone({'id': N})` 으로 수동 종료한다.

**게이트를 어겼다고 판단되면** 되돌리기를 시도하지 말고 **무엇을 실행했는지 커밋 해시와 함께 즉시 보고**한다(§3).

### 하드 가드

- 대상에 **`-a` 계열(`hotfix/v*-a`)이 포함되면 진행하지 않는다.** 경고하고 제외한다
- **`-a` ↔ 본선 머지는 수행하지 않는다.** 사용자가 명시로 지시해도 한 번 더 확인받는다
- 본선 → `-a` 기능 이식은 cherry-pick 성격이다. 머지와 분리해 별도 작업으로 다룬다

### 단계별 수행

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 2 | `planner` 서브에이전트 (Fable 5.1) | 브리핑의 충돌 파일을 읽고 **"두 기능이 모두 살아나려면 어떻게 통합해야 하는가"** 를 판단. 파일별 해결 지침 문서를 낸다. Edit/Write 권한이 없어 직접 손대지 못한다 |
| 3 | `implementer` 서브에이전트 (Sonnet 5) | 2단계 지침대로 머지·충돌 해소 |
| 4 | **부모 세션이 직접** (Opus 5) | 두 기능이 **모두** 동작하는지, 최종 형태가 의도에 맞는지 검수. **무단 커밋·머지 발생 여부를 반드시 함께 점검한다**(§3) |

- 2단계 모델은 **머지를 시작한 쪽의 최상위 모델**을 쓴다. Claude 세션이므로 `planner`(Fable 5.1)다. 한도에 걸리면 `planner-fallback`(Opus 5)으로 잇는다
- 변경이 매우 커서 부모가 전체 diff 를 읽기 어려우면 4단계만 영역별로 `reviewer` 에 나눠 맡기고 **종합 판단은 부모가** 한다

## 11. 협업 방식

이 협업 규칙은 모든 세션과 서브에이전트에 적용된다.

- **한 번에 하나의 결정만**: **바로 다음 결정**에 대해서만 선택지와 트레이드오프를 제시한다. 앞선 결정이 나기 전에 여러 단계짜리 해법 매트릭스·분기 표·"고칠 파일" 목록·변경 후 작업 트리를 미리 깔지 않는다 — 그런 요소는 아직 나지 않은 결정에 의존하며, 결정권을 사용자에게서 빼앗아 온다.
- **조사는 깊게, 노출은 좁게**: 분석·탐색은 내부적으로 철저히 하되, 사용자에게 도달하는 것은 초점이 좁은 하나의 질문과 선택지다.
- **흐름 끝 요약은 좋다**: 모든 결정이 끝난 뒤, 변경 세트·영향 파일·브랜치 매트릭스를 마지막에 요약해(확인용) 보여주는 것은 환영한다.
- **예외 — 명시적 요청**: 사용자가 직접 여러 옵션이나 옵션 매트릭스를 요청하면("내 선택지가 뭐야", "목록으로 줘") 제공한다.
- **암묵적 확장 금지**: 사용자가 승인한 작업이 다른 후속 작업을 암시하는 것처럼 보여도, 조용히 범위를 넓히지 않는다. 후보 후속 작업은 별도의 결정으로 표면화한다.
- **제안한 규칙은 명시 선택 후 반영**: §2 "계획 세션도 마찬가지 — 제안한 규칙은 명시 승인 뒤에 반영" 절과 같은 내용이다.
